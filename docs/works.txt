4. PROBLEMS HIT AND HOW EACH WAS FIXED
-------------------------------------
  (a) QAIRT download truncated (777 MB instead of 1.35 GB; "End of Central Directory").
      Fix: resumed with curl.exe -C - (HTTP range), then checked the archive with tar -tf.

  (b) My mistake: deleted the extracted SDK. Windows treats "qairt" and "QAIRT" as the
      same folder. Fix: extracted again from the zip.

  (c) install_executorch.py failed: "unknown type name 'uint'" in vec128_uint_aarch64.h.
      Cause: on an ARM64 host the Visual Studio generator defaults to ARM64, so the C++
      part of the Python package built for ARM64 while Python is x64.
      Fix: CMAKE_GENERATOR="Visual Studio 17 2022" and CMAKE_GENERATOR_PLATFORM=x64
      (CMake ignores the platform setting unless the generator is also set).
      Clear both before running build.ps1, which passes -G/-A itself.

  (d) build.ps1 died on a harmless gflags CMake deprecation warning.
      Cause: PowerShell 5.1 turns native stderr into terminating errors when the output is
      piped (*>&1 | Tee-Object) and the script uses $ErrorActionPreference='Stop'.
      Fix: run it in a child process with cmd /c "... > log 2>&1".

  (e) DeepLab export: ModuleNotFoundError: pydot.
      Cause: install_executorch.py doesn't install backends\qualcomm\requirements.txt.
      Fix: pip install -r backends\qualcomm\requirements.txt pandas

  (f) DeepLab export: "Failed to initialize QNN backend for kHtpBackend".
      Cause: QNN's envsetup.ps1 puts the host shell's (ARM64) DLLs on PATH, but the x64
      Python export can only load the x86_64-windows-msvc QnnHtp.dll.
      Fix: et-env.ps1 removes the aarch64 QNN paths and adds lib\ and bin\x86_64-windows-msvc.
      (The ARM64 runner uses its own copies next to it in xelite-run.)

  (g) RUNNER CRASH ON EXIT, fixed in source. Details in section 5.

5. THE RUNNER CRASH: WHERE AND WHY
----------------------------------
  Symptom : qnn_executor_runner.exe finished every inference, wrote its outputs and
            "Write etdump ... Size = 3384", then died.
            Windows Event Log (Application Error 1000):
              faulting module ntdll.dll, 0xC0000374 STATUS_HEAP_CORRUPTION (offset 0x1115b8)
              and once 0xC0000409 (fail-fast)
  Where   : examples\qualcomm\executor_runner\qnn_executor_runner.cpp, end of main():
              FILE* f = fopen(FLAGS_etdump_path.c_str(), "w+");   // bug 2
              fwrite(result.buf, 1, result.size, f);
              fclose(f);
              free(result.buf);                                   // bug 1
  Bug 1 (the crash):
            result.buf comes from flatcc_builder_finalize_aligned_buffer(). On MSVC,
            flatcc implements aligned allocation as _aligned_malloc
            (third-party\flatcc\include\flatcc\portable\paligned_alloc.h:121-123,
            "Aligned _aligned_malloc is not compatible with free"). Plain free() on that
            pointer corrupts the heap, and ntdll detects it -> 0xC0000374.
            On Linux/Android the allocator is posix_memalign, where free() is correct.
            That's why this only crashes on Windows.
  Bug 2 (silent data corruption):
            "w+" is TEXT mode on Windows, so every 0x0A byte is written as 0x0D 0x0A.
            Evidence: the log said 3384 bytes, the file had 3388 bytes with exactly 4 CRLF
            pairs. This is why the ExecuTorch Inspector couldn't parse the profile.
  Fix     : fopen(..., "wb") and flatcc_builder_aligned_free(result.buf)
            (+ an extern "C" declaration; the function is in flatcc's runtime, linked via etdump)
  Verified: load test, profile_level 2 and the 10+100-iteration benchmark all exit 0;
            ETDump size on disk == logged size (3384/3384, 343464/343464); no new crash
            events; accuracy unchanged; Inspector now reads the profile.
  Scope   : only qnn_executor_runner.cpp has this pattern. The LLM runners don't.
  Note    : this is a local patch to upstream v1.5.1. Re-apply it if ExecuTorch is
            re-cloned (worth reporting upstream).
